# 士兵运动断续：诊断与修复报告

日期：2026-09-19。主工程：deskfront-jevlab。构建：`main-74878b8b6152`。

## 结论

问题发生在游戏 AI 和 LLM 共用的运动执行层，不能靠缩短模型响应时间解决。已修复路径节点造成的停步、动画状态机时钟被步速拖慢，以及 LLM 快照触发的集中寻路。

## 根因及修改

1. **中间节点被当成停车。** `scripts/unit.gd` 原先每帧只移除一个到达的节点，这一帧不调用 `advance_drive`，随后 `presentation_tick` 调用 `advance_idle`，将速度清零并切回待机。现在先连续消费已经到达的节点，同一帧继续向下一个节点移动；最终抵达、真实障碍和明确停令仍然停车。保留拐角通行验证。
2. **过渡时钟与步速耦合。** `scripts/toy_actor.gd` 原先给整个 AnimationTree 乘根运动倍率，缓慢起步时连 0.15 秒的状态过渡也被拉长；紧接停止的再次起步会等待旧过渡完成。现在用每个移动状态内的 TimeScale 调节步频，状态机按仿真时间推进。位移仍从动画根运动提取，保持加速、制动、脚底锁定与碰撞。
3. **读取状态时集中寻路。** `scripts/tactics.gd` 的 `flag_hint` 曾在九名士兵的快照读取中同步计算路线。现在快照只读缓存；每 0.1 秒最多刷新一名士兵的建议。缓存过期或地图变化返回 `pending`，不会提供失效路线；夺旗预警仍由引擎即时生成。

## 回归结果

- 相同可通行走廊、14 个路径节点、60 Hz 仿真：修复前游戏 AI / LM 各有 **24 帧意外停步**，修复后均为 **0**。该测试隔离共用执行层，没有网络推理延迟或敌人交战干扰；并非宣称所有战术停车都应消失。
- LLM 冷缓存快照中位耗时：**20.34 ms → 0.69 ms**，同一台 Mac 的原生 headless 测量，不等于跨设备性能保证。
- 新增断言覆盖：快照零寻路、分批刷新、九人覆盖、导航变化失效、慢速蹲走过渡 0.4 秒内完成。
- 完整 `python3 tools/project.py test` 通过：语义、集成、战斗、夺旗、LLM、炮组、小楼通路、冲锋/防滑、脚底高度、2349 个人体姿态采样、布娃娃及 **51 项 Python 测试**。
- Godot Forge Web 发布门禁通过；构建已导出到主游戏 `build/web`。

## 网页实机验证

实测游戏 AI / LM 帧间隔中位数均为 **8.3 ms**，P95 均为 **9.2 ms**；游戏运行错误为零，音频处于 running。详见 `web.json`，使用真正 Godot Web 构建、真实页面控制切换及画布点击，检查音频解锁、运行时构建号与控制模式。LLM 使用隔离的确定性测试客户端，不调用云模型；这项验证不衡量云端推理质量或响应延迟。Apple M4 Max / ANGLE Metal 硬件加速浏览器与自动化软件渲染的帧率不可混为一谈。浏览器缺少 favicon 的 404 单独记录为非游戏警告。
